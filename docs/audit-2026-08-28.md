## 三、P1 问题详情与修复建议

### P1-1 CacheRedisDriver.ensureReady 死循环

**根因**：`readyPromise` 用 `.catch()` 吞掉了连接失败，导致 `readyPromise` 永不 reject；`ensureReady` 检测到 `!isReady` 时进入每 10ms 一次的无限轮询，无超时、无重试、无错误传播。

```ts
// 现状（第 49-56 行）
this.readyPromise = this.client.connect()
  .then(() => console.log(...))
  .catch((err) => console.error('Failed to connect:', err))  // 吞错，readyPromise 永不 reject
```

**建议修复**：连接失败时保留错误并让 `ensureReady` 快速失败（带超时），而不是无限轮询。

### P1-2 解密明文泄露进日志

**根因**：`cryptoTool.decrypt` 在 JSON.parse 失败时，错误信息拼入了 `Decrypted content: "<明文前100字符>"`；而 `DecryptRequest.ts:94-104` 的 `log.error` 完整记录了 `err.message`，导致解密明文进入服务端日志。

**建议修复**：错误信息只保留长度/摘要等元信息，绝不含明文片段。

### P1-3 跨进程事件本地丢失

**根因**：`crossProcessBus.subscribe` 将 handler 存入 `localHandlers`，仅靠 Redis subscriber 回环触发；`publish` 中的 `eventBus.emit` 只触发 `eventBus` 上的 listener（非 `localHandlers`）。Redis 不可用时，`localHandlers` 的事件静默丢失。

**建议修复**：`publish` 时本地直接触发 `localHandlers`（配合去重标记），或 `subscribe` 同时注册本地派发。

### P1-4 APP_KEY 长度校验不一致

**根因**：`validateSecurityConfig` 对非 32 字节 `APP_KEY` 仅 `console.warn`（文案还声称「已自动补齐或截断」），但 `CryptoTool.getKey()` 直接 `Buffer.from(k)` + `assertKeyLength` 强制抛错；且 key 未做 SHA-256 派生（而 IV 做了派生）。配置非 32 字节 key 时，启动仅告警、运行期加密即崩溃。

**建议修复**：key 与 IV 一致做 SHA-256 派生为 32 字节，或在启动期强制校验并拒绝启动。

## 四、做得好的地方

- **SQL 安全**：`orderByRaw`/`raw` 全部使用 `??`/`?` 参数绑定，无拼接注入。
- **批量操作防护**：`modifyByFilters`/`deleteByFilters`/`forceDelete` 均拒绝空 filter，防全表误操作。
- **敏感字段裁剪**：`EncryptResponse.omitByPath` 递归裁剪密码/token/OSS 凭证，且覆盖嵌套对象。
- **密码哈希**：scrypt（抗 GPU 爆破）+ timingSafeEqual 恒时比较，已废弃 MD5 导出。
- **加密升级**：AES-256-GCM（认证加密）替代 CBC，消除 padding oracle。
- **队列健壮性**：`FOR UPDATE SKIP LOCKED` 防并发、超时任务释放、DB 连接保活与优雅退出。
- **类型收窄**：`as unknown as` 虽 26 处，但均合法（替代 any 的 unknown + 类型守卫，符合规范）。
